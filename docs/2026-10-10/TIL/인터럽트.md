## 1. 외부 인터럽트 vs 내부 인터럽트

> **"내 코드가 실행해서 생겼나(내부), 코드와 상관없이 바깥 장치가 보냈나(외부)"로 구분합니다.**

```
외부 인터럽트                          내부 인터럽트
─────────────                         ─────────────
타이머 / 키보드 / 디스크 / 시리얼       int 0x30 (시스템콜), 페이지 폴트,
        │ (CPU 밖 하드웨어)            0으로 나누기, 잘못된 메모리 접근
        ▼                                     │ (지금 실행 중인 명령어 자체)
   언제든 끼어듦 (비동기)                      ▼
                                       그 명령어를 실행할 때만 발생 (동기)
```

| | 외부 인터럽트 (External) | 내부 인터럽트 (Internal) |
|---|---|---|
| 발생 원인 | CPU 바깥의 하드웨어 | 현재 실행 중인 명령어 자체 |
| 발생 시점 | 비동기: 코드와 무관하게 언제든 | 동기: 특정 명령어를 실행할 때만 |
| 다른 이름 | IRQ, 하드웨어 인터럽트 | 예외(exception), 트랩, 폴트, 소프트웨어 인터럽트 |
| Pintos 벡터 | `0x20 ~ 0x2f` | `0x00 ~ 0x1f` (CPU 예외), `0x30` (시스템콜) |
| 등록 함수 | `intr_register_ext` | `intr_register_int` |
| `intr_context()` | `true` | `false` |
| 핸들러 진입 시 | 인터럽트 **자동으로 꺼짐** | 켜진 채로 처리 가능 |
| 핸들러 안에서 sleep | **불가능** | 가능 |
| EOI(처리 끝 신호) | 필요 (PIC에 보냄) | 필요 없음 |

코드로 확인: `pintos/threads/interrupt.c:342`

```c
external = frame->vec_no >= 0x20 && frame->vec_no < 0x30;
if (external) {
    ASSERT (intr_get_level () == INTR_OFF);
    in_external_intr = true;    // 이때부터 intr_context()가 true
}
```

내부 인터럽트는 "유저 프로세스가 커널에게 일을 시킨 것"이라 커널이 그 프로세스를 대신해 잠들 수 있습니다.
외부 인터럽트는 **아무 스레드나 중간에 끊고 들어온 것**이라, 그 안에서 잠들거나 스케줄링하면 안 됩니다.

## 2. 타이머 인터럽트도 외부 인터럽트인가

> **네. 타이머 칩(8254)이라는 CPU 밖의 장치가 보내는 신호이기 때문입니다.**

```
8254 타이머 칩 ──(10ms마다, 100Hz)──▶ IRQ 0 ──▶ 벡터 0x20 ──▶ timer_interrupt()
   (CPU와 별개로 자기 클럭을 셈)
```

- 8254 칩이 CPU와 상관없이 일정 주기(`TIMER_FREQ` = 100Hz)로 신호를 보냅니다.
- CPU는 그때 무슨 코드를 실행 중이든 끊기고 핸들러로 점프합니다.
- `timer_init()`에서 `intr_register_ext (0x20, timer_interrupt, "8254 Timer")`로 등록합니다. **`_ext`로 등록한다는 점**이 외부 인터럽트라는 증거입니다.

### "계속 발생해서 외부 인터럽트"가 아닙니다

주기적이라는 건 타이머의 특성일 뿐이고, 외부 인터럽트인 이유는 **CPU 밖의 장치가 보냈기 때문**입니다.

| | 누가 신호를 보내나 | 언제 | 분류 |
|---|---|---|---|
| 타이머 (IRQ 0) | 8254 칩 | 10ms마다 계속 | 외부 |
| 키보드 (IRQ 1) | 8042 칩 | 키 누를 때 | 외부 |
| 시스템콜 (`int 0x30`) | CPU가 실행하는 코드 자신 | 그 명령어를 실행할 때 | 내부 |

키보드는 주기적이지 않지만 똑같이 외부 인터럽트입니다.
반대로 소프트웨어가 일정 주기로 `int`를 실행해도 그건 외부 인터럽트가 아닙니다.

## 3. IRQ란 무엇인가

> **IRQ(Interrupt ReQuest)는 장치가 CPU에게 처리를 요청할 때 쓰는 물리적인 신호선입니다.**

```
타이머 칩 ──IRQ 0──┐
키보드 ────IRQ 1──┤
(slave PIC)IRQ 2──┤    PIC            CPU
시리얼 ────IRQ 4──┼─ (인터럽트 ──────▶ (인터럽트 핀)
디스크 ────IRQ14──┤   컨트롤러)
              ...  ┘
```

- 장치마다 PIC(인터럽트 컨트롤러)의 입력 핀이 정해져 있습니다.
- 장치가 그 핀에 신호를 보내면 PIC가 CPU에 전달합니다.

### IRQ 번호와 벡터 번호는 다릅니다

| | IRQ 번호 | 벡터 번호 |
|---|---|---|
| 정체 | 장치가 쓰는 하드웨어 라인 (물리) | CPU가 어떤 핸들러를 부를지 고르는 번호 (소프트웨어) |
| Pintos 관계 | `IRQ n` | `0x20 + n` |

`devices/` 아래 `intr_register_ext` 호출로 확인:

| 장치 | 벡터 | IRQ | 파일 |
|---|---|---|---|
| 8254 타이머 | `0x20` | IRQ 0 | `timer.c:49` |
| 8042 키보드 | `0x21` | IRQ 1 | `kbd.c:31` |
| 시리얼 | `0x20 + 4` | IRQ 4 | `serial.c:88` |
| 디스크 | `c->irq` | IRQ 14, 15 | `disk.c:140` |

### 벡터가 `0x20`부터 시작하는 이유

PIC의 기본 설정은 IRQ 0~7을 벡터 0~7로 보내는데, 이 범위는 CPU 예외(페이지 폴트 등)가 이미 쓰고 있어서 충돌합니다.
그래서 `pic_init()`이 PIC를 재설정해 IRQ 0~15를 벡터 `0x20~0x2f`로 옮깁니다 (`interrupt.c:298`).

```c
outb (0x21, 0x20); /* ICW2: 라인 IR0...7 -> irq 0x20...0x27. */
```

### EOI

외부 인터럽트는 핸들러가 끝나면 PIC에 "이 IRQ 처리 끝났어"라고 알려야 합니다 (`pic_end_of_interrupt()`, `interrupt.c:313`).
알려 주지 않으면 PIC는 그 IRQ를 **다시는 전달하지 않습니다.** 장치가 보낸 요청이라서 필요한 절차이고, 내부 인터럽트에는 없습니다.

## 4. 외부 인터럽트 핸들러의 제약

> **핸들러 안에서는 잠들 수도, 직접 양보할 수도 없습니다.**

```
스레드 A 실행 중
     │  ← 타이머 IRQ (A는 이 사실을 모름)
     ▼
timer_interrupt()   ← 인터럽트 OFF 상태, intr_context() == true
     │  하면 안 되는 것: lock_acquire, sema_down, thread_block, thread_yield
     ▼
스레드 A 계속 (또는 intr_yield_on_return 예약이 있으면 끝난 뒤 양보)
```

1. **인터럽트가 이미 꺼진 상태로 진입**합니다. 핸들러 안에서 `intr_disable()`을 또 부를 필요가 없습니다.
2. **잠들거나 블록할 수 없습니다.** `lock_acquire`, `sema_down`, `thread_block()`은 `ASSERT (!intr_context ())`에 걸립니다.
3. **`thread_yield()`를 직접 부르면 안 됩니다.** 양보가 필요하면 `intr_yield_on_return()`으로 예약하고, 핸들러가 끝난 뒤 양보가 일어나게 합니다 (`interrupt.c:269`).
4. **핸들러는 짧게** 끝내야 합니다. 틱마다 실행되는 코드라 느리면 시스템 전체가 느려집니다.

핸들러가 락을 못 쓰기 때문에, **핸들러와 공유하는 데이터는 락 대신 인터럽트 끄기로 보호**해야 합니다 (5장).

## 5. 인터럽트는 언제 끄고 언제 켜두나

> **공유 데이터를 읽고 쓰는 동안 중간에 끊기면 안 되는 구간(임계 구역)에서만, 최대한 짧게 끕니다.**

### 꺼야 하는 경우

- **스레드 코드와 인터럽트 핸들러가 같이 접근하는 데이터**를 건드릴 때.
  - 예: `timer_interrupt`가 읽는 `sleep_list`를 `timer_sleep`에서 수정할 때
- ready list, waiters 리스트 같은 **스케줄러 자료구조**를 조작할 때.
  - 예: `sema_down`, `sema_up` (`threads/synch.c:67`, `88`, `111`)
- `thread_block()`을 호출할 때. 반드시 꺼진 상태에서만 호출할 수 있습니다.

### 켜 두어야 하는 경우 (끄면 안 되는 경우)

- **락이나 세마포어로 보호할 수 있는 구간.** 락이 가능하면 락을 쓰는 것이 원칙입니다.
- **오래 걸리는 작업.** 오래 끄면 타이머 틱과 키보드 입력을 놓치고 응답성이 떨어집니다.
- **잠들 수 있는 작업** (`sema_down`, `lock_acquire`, 메모리 할당 등). 끈 채로 잠들면 안 됩니다.

### 판단 순서

```
이 데이터를 인터럽트 핸들러도 만지나?
   ├─ 예 ─▶ 인터럽트 끄기 (핸들러는 락을 못 쓰므로)
   └─ 아니오 ─▶ 스레드끼리만 공유하나?
                  ├─ 예 ─▶ 락 / 세마포어
                  └─ 아니오 ─▶ 보호 불필요
```

## 6. 인터럽트를 끄는 올바른 방법

> **`intr_enable()`로 켜지 말고, 저장해 둔 이전 상태로 복원합니다.**

```c
enum intr_level old_level = intr_disable ();  // 현재 상태를 저장하고 끔
/* 임계 구역: 최대한 짧게 */
intr_set_level (old_level);                   // 원래 상태로 복원
```

- 호출 시점에 **이미 꺼져 있었다면** 그냥 `intr_enable()`로 켜 버리는 순간 바깥쪽 임계 구역이 깨집니다.
- 그래서 항상 "끄기 전 상태를 저장 → 끝나면 그 상태로 복원" 패턴을 씁니다.
- 구간은 **필요한 줄만** 감쌉니다.

## 7. 알람 클럭과의 연결

> **`timer_sleep`(스레드 컨텍스트)과 `timer_interrupt`(외부 인터럽트 컨텍스트)가 `sleep_list`를 같이 만지기 때문에 인터럽트를 꺼야 합니다.**

```
timer_sleep()  [스레드 컨텍스트]            timer_interrupt()  [외부 인터럽트 컨텍스트]
  intr_disable                                (이미 인터럽트 OFF 상태로 진입)
  sleep_list에 삽입                           매 틱마다 sleep_list를 훑음
  thread_block                                깰 시간이 된 스레드를 thread_unblock
  intr_set_level
```

- 락으로는 해결되지 않습니다. 핸들러가 락을 못 얻기 때문입니다.
- 위 5장의 "스레드와 핸들러가 공유하는 데이터는 인터럽트로 보호"하는 대표적인 예입니다.

### `timer_ticks()`의 짧은 보호 구간

`devices/timer.c:80`

```c
enum intr_level old_level = intr_disable ();
int64_t t = ticks;
intr_set_level (old_level);
```

- 아무것도 안 하는 것처럼 보이지만, **`ticks`(64비트)를 한 번에 안전하게 읽기 위한 보호**입니다.
- 32비트 x86에서는 64비트 값을 읽는 도중에 타이머 인터럽트가 `ticks`를 올리면 앞/뒤 절반이 서로 다른 시점의 값이 될 수 있습니다.
- 그래서 읽는 순간만 인터럽트를 끕니다. "끄는 구간은 짧게"의 좋은 예입니다.

## 8. 한눈에 보는 요약

| 질문 | 답 |
|---|---|
| 외부 / 내부 구분 기준 | 바깥 장치가 보냈나, 내 명령어가 만들었나 |
| 타이머는? | 외부 (8254 칩, IRQ 0, 벡터 `0x20`) |
| IRQ란? | 장치가 쓰는 하드웨어 요청 라인. 벡터 = `0x20 + IRQ` |
| 외부 핸들러에서 못 하는 것 | 잠들기, 락 획득, `thread_yield` 직접 호출 |
| 인터럽트를 꺼야 할 때 | 핸들러와 공유하는 데이터, 스케줄러 자료구조, `thread_block` |
| 켜 두어야 할 때 | 락으로 보호 가능한 구간, 오래 걸리는 작업, 잠들 수 있는 작업 |
| 끄는 방법 | `old = intr_disable()` → 작업 → `intr_set_level(old)` |
