## 1. 알람 클럭이 왜 필요한가

> **기다리는 동안 CPU를 다른 스레드에게 넘기기 위해서입니다.**

처음 코드(`busy waiting`)는 시간이 될 때까지 계속 "아직이야?" 하고 확인합니다.
기다리는 내내 CPU가 쉬지 못하고 일만 하므로 **낭비**입니다.

| | busy waiting (처음 코드) | 재우는 방식 (목표) |
|---|---|---|
| 기다리는 동안 | 계속 시간을 확인함 | 잠들어서 CPU를 안 씀 |
| CPU 상태 | 쉬지 못하고 계속 일함 | 할 일이 없으면 쉼 |
| idle ticks | 거의 0 | 크게 늘어남 |

**idle ticks**는 CPU가 할 일이 없어 쉰 시간입니다.
구현이 잘 됐는지는 테스트 통과 여부가 아니라 `idle ticks`가 늘었는지로 확인합니다.
busy waiting도 깨어나는 시각은 맞게 내서 테스트를 통과하기 때문입니다.

> 스레드가 하나뿐이면 busy waiting이어도 손해가 없습니다.
> 하지만 이 테스트들은 스레드 여러 개가 번갈아 도는 것을 전제로 하므로 알람 클럭이 필요합니다.

## 2. 구현의 큰 흐름

> **"몇 시에 깨울지 적어 두고 재운다 → 타이머가 때가 되면 깨운다"**

```
timer_sleep (스레드가 호출)               timer_interrupt (10ms마다 자동 실행)
────────────────────────                  ─────────────────────────────────
깨울 시각 = 지금 + 잘 시간                  시간이 지났는지 확인
깨울 시각을 내 구조체에 적어 둠              잘 만큼 잔 스레드를 찾아서
sleep_list에 넣음 (깨울 시각 순서로)         ready_list로 보냄
잠듦 (thread_block)
      ...                  ◀───────────── 깨워짐
이어서 실행
```

- **깨울 시각은 "몇 틱 뒤"가 아니라 "몇 시"로 저장**합니다. 한 번 적으면 끝이고, 비교는 `깨울 시각 <= 지금`만 보면 됩니다.
- 깨울 시각은 스레드마다 달라서 **각자의 `struct thread` 안**에 멤버를 추가해 저장합니다.
- 깨우는 일은 `timer_interrupt`에서 합니다. 스레드들이 전부 자고 있어도 때가 되면 알아서 불리는 곳이 거기뿐이기 때문입니다.

## 3. 타이머 인터럽트는 누가 부르나

> **어떤 코드도 직접 부르지 않습니다. 하드웨어 타이머가 CPU를 깨워서 실행됩니다.**

```
타이머 칩 ──(1초에 100번 신호)──▶ CPU ──▶ 하던 일 잠깐 멈춤 ──▶ timer_interrupt 실행
                                                              │
                                    ◀──── 멈췄던 곳부터 다시 실행 ┘
```

- `timer_init`에서 타이머 칩에 "1초에 100번 신호를 보내라"고 설정하고(`TIMER_FREQ = 100`), "신호가 오면 `timer_interrupt`를 실행하라"고 등록해 둡니다.
- 신호 한 번이 **1 tick(10ms)** 입니다.
- `ticks`는 부팅 후 이 함수가 불린 횟수이고, `timer_ticks()`가 돌려주는 값입니다.
- 인터럽트를 꺼 두면 신호가 와도 바로 처리하지 못하고 켜질 때까지 기다립니다. 그래서 끄는 구간은 짧아야 합니다.

### 코드에 호출문이 없는 이유

`timer_interrupt (...)`처럼 직접 부르는 줄은 코드 어디에도 없습니다.
**함수 이름을 번호표에 적어 두고, 신호가 오면 번호로 찾아서 부르는 구조**이기 때문입니다.

```
① 타이머 칩이 신호를 보냄 (0x20번)
        ▼
② CPU가 하던 일을 멈추고, 인터럽트 표에서 0x20번 항목으로 이동
        ▼
③ 어셈블리 코드(intr-stubs.S)가 레지스터를 저장하고 intr_handler를 호출
        ▼
④ intr_handler가 "0x20번에 등록된 함수"를 배열에서 찾아 호출
        ▼
⑤ timer_interrupt 실행
```

| 단계 | 코드 | 하는 일 |
|---|---|---|
| 등록 | `timer_init`의 `intr_register_ext (0x20, timer_interrupt, ...)` | 0x20번에 `timer_interrupt`를 연결 |
| 보관 | `register_handler` | 배열 `intr_handlers[0x20]`에 함수 주소를 저장 |
| 실행 | `intr_handler` | 번호로 배열에서 찾아 `handler (frame)`으로 호출 |

- `list_sort`가 받은 `less`를 부르는 것과 같은 방식입니다. **함수 포인터**를 저장해 두었다가 나중에 부릅니다.
- 핸들러가 끝나면 칩에게 "처리 끝"을 알려 줍니다. 이걸 해야 칩이 다음 신호를 보냅니다.

### 일정 시간이 지나면 일어나는 일: 양보 (재우는 게 아님)

> **한 스레드가 4틱(40ms)을 연속으로 쓰면, 실행 대기 줄 맨 뒤로 보내고 다음 스레드에게 CPU를 넘깁니다.**

`timer_interrupt`가 매 틱마다 `thread_tick`을 부르고, 거기서 이렇게 판단합니다.

```
스레드가 쓴 틱 수를 셈 → 4틱이 되면 "핸들러가 끝나면 양보하라"고 표시
핸들러가 끝난 뒤 → thread_yield → ready_list 맨 뒤로 보냄
```

**양보와 재우기는 다릅니다.**

| | 양보 (`thread_yield`) | 재우기 (`thread_block`) |
|---|---|---|
| 상태 | `READY` (언제든 돌 수 있음) | `BLOCKED` (깨워 줄 때까지 못 돎) |
| 가는 곳 | `ready_list` 맨 뒤 | `sleep_list` 같은 다른 대기 줄 |
| 다시 돌려면 | 자기 차례가 오면 바로 | 누가 `thread_unblock`으로 깨워야 함 |
| 언제 | 시간을 다 썼을 때, 스스로 양보할 때 | 어떤 조건을 기다릴 때 |

```
양보:   [실행] ─4틱 사용→ ready_list 맨 뒤 ─차례가 오면→ [실행]
재우기: [실행] ─timer_sleep→ sleep_list ─때가 되면 깨움→ ready_list ─→ [실행]
```

- 처음 busy waiting 코드는 `thread_yield`로 계속 양보하며 돌았습니다. 그래서 READY 상태로 계속 돌아와 CPU가 쉬지 못했습니다.
- 새 방식은 BLOCKED로 가서 깨울 때까지 돌아오지 않으므로 CPU가 쉽니다.
- 인터럽트 처리 안에서는 `thread_yield`를 직접 쓸 수 없고, "끝나면 양보하라"는 표시만 해 둡니다. 처리 도중에 다른 스레드로 넘어가면 안 되기 때문입니다.

## 4. 재우는 동안 인터럽트를 끄는 이유

> **`sleep_list`를 고치는 도중에 인터럽트가 같은 리스트를 읽으면 리스트가 깨지기 때문입니다.**

### 주된 이유: 리스트가 반쯤 연결된 상태를 읽음

리스트에 원소를 넣는 일은 연결 고리(앞/뒤 포인터)를 **여러 개 차례로** 바꾸는 작업입니다.
그 한가운데에 인터럽트가 끼어들면 이런 일이 생깁니다.

```
스레드 A                                타이머 인터럽트
────────                                ──────────────
sleep_list에 A를 넣는 중
  (앞 포인터는 바꿨고, 뒤 포인터는 아직...)
                      ── 끼어듦 ──▶      같은 sleep_list의 맨 앞을 읽음
                                         반쯤 연결된 상태를 봄 → 리스트가 깨짐
```

- 깨울 시각이 한참 남았어도 일어납니다. 인터럽트는 확인하러 **리스트를 읽기만 해도** 문제이기 때문입니다.
- 이 이유는 시각이나 확률과 상관없이, 리스트를 수정하는 명령어 한가운데에 끼어들기만 하면 일어납니다.

### 보조 이유: 등록과 재우기 사이의 틈

"리스트에 넣기"와 "재우기(`thread_block`)" 사이에도 틈이 있습니다.
타이머 인터럽트는 한 스레드가 정해진 시간을 쓰면 다른 스레드로 넘기는 일도 하기 때문에, 그 틈에 A가 쫓겨나 한참 못 돌아올 수 있습니다.

```
A: sleep_list에 넣음
     ── 인터럽트, A는 시간을 다 썼다고 판단 ──▶ 다른 스레드로 전환
     (B, C가 한참 돔... 틱이 계속 올라가 A의 깨울 시각이 지남)
     인터럽트가 A를 깨우려 함 → A는 아직 잠들기 전 (실행 대기 상태)
     "잠든 스레드만 깨울 수 있다"는 검사에 걸려 멈춤
```

- 이 경우는 일어날 확률이 낮습니다. 넣고 재우기까지 명령어 몇 줄뿐이라서 `timer_sleep(1)`처럼 아주 짧게 재우거나, 하필 그 틈에 시간을 다 써서 쫓겨나는 경우에만 생깁니다.
- 하지만 **0은 아니어서** 가끔만 터지는 재현하기 어려운 버그가 됩니다.

### 결론

- **리스트 수정과 `thread_block`을 한 덩어리로 묶어서** 끝낸 뒤에 인터럽트를 켭니다.
- 복원은 `intr_enable()`로 켜는 게 아니라 **처음 상태로 되돌리는** `intr_set_level (old)`를 씁니다. 이미 꺼진 채로 불린 경우를 깨뜨리지 않기 위해서입니다.
- 락을 쓰지 않는 이유: 인터럽트 처리 중에는 잠들 수 없어서 락을 기다릴 수 없습니다.

| 코드 | 직접 꺼야 하나 | 이유 |
|---|---|---|
| `timer_sleep` (스레드 쪽) | **꺼야 함** | 언제든 인터럽트에 끊길 수 있음 |
| `timer_interrupt` (인터럽트 쪽) | 안 꺼도 됨 | 들어올 때 이미 자동으로 꺼져 있음 |

## 5. 재운 스레드가 이어서 실행되는 이유

> **멈출 때 "어디까지 했는지"를 통째로 저장해 두고, 다시 돌 때 그대로 복원합니다.**

```
멈출 때:  CPU 레지스터 전부(다음 실행 위치, 스택 위치 포함)를
          그 스레드의 struct thread 안에 저장
다시 돌 때: 저장해 둔 값을 CPU에 되돌림
          → 멈췄던 바로 다음 줄부터 실행
```

- 스레드마다 **자기 전용 스택**이 따로 있어서 지역 변수와 함수 호출 기록이 섞이지 않습니다.
- 재워진 스레드 입장에서는 `thread_block()`이 "그냥 오래 걸린 함수 호출"처럼 보입니다. 자기가 멈췄었다는 걸 모릅니다.

## 6. 리스트는 어디에 만드나

> **`sleep_list`는 `timer.c`에 `static`으로 둡니다. `ready_list`로 옮기는 일은 `thread_unblock`이 대신 합니다.**

| 파일 | 가진 리스트 | 하는 일 |
|---|---|---|
| `timer.c` | `sleep_list` | 재울 스레드 보관, 깨울 때가 됐는지 판단 |
| `thread.c` | `ready_list` | `thread_unblock`이 스레드를 실행 대기 상태로 바꾸고 넣음 |

- 깨울 스레드를 **고르는 일**은 `timer.c`에서, **ready로 옮기는 일**은 `thread.c`의 `thread_unblock`을 불러서 합니다.
- 리스트 포인터를 다른 파일에 넘길 필요가 없습니다. 각 파일은 자기 리스트만 만지고, 파일 사이는 **함수 호출**로만 연결합니다.
- 리스트는 선언만으로 쓸 수 없고 `timer_init`에서 `list_init`으로 **비어 있는 리스트로 초기화**해야 합니다.
- `timer.c`에 `list.h`를 직접 include하지 않아도 `thread.h`가 이미 include하고 있어서 쓸 수 있습니다.
- 스레드를 리스트에 꽂는 고리가 `struct thread`의 `elem`입니다. 재워진 스레드는 `ready_list`에 없으므로 같은 `elem`을 같이 써도 충돌하지 않습니다.

## 7. 정렬해서 넣는 이유

> **넣을 때 정렬해 두면, 깨울 때는 맨 앞만 보면 됩니다.**

```
sleep_list (깨울 시각 순서): [A:100] [B:105] [C:105] [D:120]    지금 = 105

A: 100 <= 105 → 깨움
B: 105 <= 105 → 깨움
C: 105 <= 105 → 깨움
D: 120 <= 105 ? 아니오 → 여기서 멈춤 (뒤는 더 늦으니 볼 필요 없음)
```

| | 넣을 때 정렬 (권장) | 정렬 안 함 |
|---|---|---|
| 재울 때 | 자리를 찾아야 함 | 맨 뒤에 붙이기만 하면 됨 |
| 깨울 때 | 보통 맨 앞만 확인 | 매번 전부 훑어야 함 |

- 재우는 일은 가끔이지만 깨우는 확인은 **1초에 100번** 일어나므로, 자주 하는 쪽을 가볍게 만드는 것이 이득입니다.
- 같은 시각에 여러 스레드가 깨어날 수 있어서 `if`가 아니라 **맨 앞이 안 될 때까지 반복**해야 합니다.

## 8. 비교 함수는 직접 만든다

> **정렬하려면 "누가 앞인지" 정하는 함수가 필요하고, Pintos는 그걸 우리가 만들도록 비워 뒀습니다.**

```c
typedef bool list_less_func (const struct list_elem *a,
                             const struct list_elem *b,
                             void *aux);
```

이 줄은 함수가 아니라 **"이런 모양의 함수"에 `list_less_func`라는 이름을 붙인 것**입니다. 구조체도 아닙니다.

| 이름 | 정체 |
|---|---|
| `list_less_func` | 함수의 **모양**에 붙인 이름 (반환형 `bool`, 인자 3개) |
| `less` | 그 모양의 함수를 받는 **매개변수 이름** (list.c 안의 빈 자리) |
| `wake_tick_less` 같은 이름 | **우리가 만들어서 넘기는 진짜 함수** |

```
list_sort / list_insert_ordered ( 리스트, 비교함수, ... )
                                          ▲
                              여기에 우리가 만든 함수 이름만 적어 넘김
```

- `list.c`에서 `less`를 찾아도 구현이 없는 게 정상입니다. 호출하는 쪽이 채워 주는 자리입니다.
- 같은 모양의 함수가 여러 개 있어도 됩니다. **이름으로 직접 골라서** 넘기기 때문에 컴파일러가 찾을 일이 없습니다.
- 우리가 만들 때 조건은 이것뿐입니다.
  - 반환형이 `bool`
  - 인자가 `const struct list_elem *` 두 개와 `void *` 하나
  - 이름은 `list_less_func`가 아닌 다른 것 (`typedef`를 붙이거나 본문을 넣으면 안 됨)
- **`a`가 `b`보다 먼저 와야 할 때만 `true`**를 돌려줍니다. 같을 때는 `false`여야 들어온 순서가 유지됩니다. (`<`는 되고 `<=`는 안 됨)
- 받는 건 `elem`이라서 `list_entry`로 스레드를 되찾아 값을 비교합니다.
- 위치는 `timer_sleep`보다 위, `static`으로 둡니다.

## 9. `aux`와 `UNUSED`

> **`aux`는 비교할 때 필요한 추가 정보를 넘기는 자리입니다. 우리는 안 씁니다.**

- 전역 변수 없이 값을 전달하고 싶을 때 쓰는 통로입니다. `list_insert_ordered`를 부를 때 넘긴 값이 비교 함수의 `aux`로 그대로 전달됩니다.
- 알람 클럭은 스레드에 저장된 깨울 시각만 비교하면 되어서 필요 없습니다.
  - 호출할 때는 `NULL`을 넘깁니다.
  - 함수에서는 `void *aux UNUSED`로 쓰면 "안 쓰는 인자" 경고가 안 납니다.

## 10. `list_insert_ordered`와 `list_sort`

> **둘 다 비교 함수로 순서를 만들지만, 하나는 "끼워 넣기", 하나는 "전체 정렬"입니다.**

| | `list_insert_ordered` | `list_sort` |
|---|---|---|
| 하는 일 | 이미 정렬된 리스트에 **하나**를 제자리에 끼워 넣음 | 리스트 **전체**를 정렬함 |
| 쓸 때 | 넣을 때마다 정렬 상태를 유지 | 값이 나중에 바뀔 수 있는 리스트를 꺼내기 전에 |
| 조건 | 리스트가 **미리 정렬되어 있어야 함** | 없음 |

```
list_insert_ordered 예: [10] [20] [40] [50] 에 30을 넣을 때
  30 < 10 ? 아니오 → 30 < 20 ? 아니오 → 30 < 40 ? 예 → 40 앞에 삽입
  결과: [10] [20] [30] [40] [50]
```

- 같은 값이면 뒤에 들어가서 들어온 순서가 유지됩니다.
- 알람 클럭의 깨울 시각은 등록한 뒤 바뀌지 않으므로 `list_insert_ordered`면 충분합니다.
- 우선순위처럼 **나중에 값이 바뀌는** 리스트는 이미 들어 있는 순서가 틀어지므로 `list_sort`가 맞습니다.

### `list_sort`는 어떻게 정렬하나 (이해용)

이미 정렬된 구간을 찾아서 **둘씩 합치기를 반복**합니다.

```
[3, 5, 1, 4, 2, 6]
 정렬된 구간 찾기:  [3,5] [1,4] [2,6]
 둘씩 합치기:       [1,3,4,5] [2,6]
 다시 합치기:       [1,2,3,4,5,6]
```

- `find_end_of_run`: 정렬이 유지되는 구간이 어디서 끝나는지 찾습니다.
- `inplace_merge`: 인접한 두 구간을 **복사 없이 연결만 바꿔서** 합칩니다. 두 번째 구간의 원소가 더 작으면 떼어서 첫 구간 사이에 끼워 넣습니다.
- 직접 부를 일은 없고, `list_sort`만 호출하면 됩니다.

## 11. 구조체와 포인터 `threads + i`

> **`threads + i`는 구조체를 `i`칸 건너뛴 곳의 주소입니다. 구조체 안으로 들어가는 게 아니라 옆 구조체로 이동합니다.**

```c
struct sleep_thread *threads;
threads = malloc (sizeof *threads * thread_cnt);   // 구조체 thread_cnt개를 이어서 할당
struct sleep_thread *t = threads + i;               // i번째 구조체의 주소
t->id = i;                                          // 그 구조체 안의 멤버에 접근
```

```
threads ─▶ [구조체0: test,id,duration,iterations]
           [구조체1: test,id,duration,iterations]  ◀─ threads + 1
           [구조체2: ...]                           ◀─ threads + 2
```

- 배열 선언(`[ ]`)이 없어도 **같은 구조체를 이어서 할당**하면 배열처럼 씁니다.
- 멤버가 배열이어야 하는 게 아닙니다. 구조체 **자체가** 여러 개 이어진 것입니다.
- 몇 바이트씩 건너뛸지는 신경 쓰지 않아도 됩니다. 포인터의 타입(`struct sleep_thread *`)이 크기를 알고 있어서 컴파일러가 `i × 구조체 크기`로 계산합니다.
- 결과적으로 `threads + i`, `&threads[i]`는 같은 뜻입니다.
- 이동은 구조체 단위(`threads + i`), 멤버 접근은 그다음 단계(`t->id`)로 구분합니다.

## 12. 현재 스레드 찾기와 `magic`

### `thread_current`는 어떻게 현재 스레드를 아는가

> **스택 위치(rsp)를 읽고, 4KB 경계로 내리면 그 페이지의 시작 = `struct thread` 주소입니다.**

```
페이지 맨 위 ┌─────────────────────┐
             │  커널 스택 (아래로 자람) │ ← rsp가 이 안 어딘가
             │      ▼               │
             ├─────────────────────┤
             │ magic               │ ← struct thread의 맨 끝
             │ tf, elem, ...       │
페이지 시작   │ tid, status ...     │ ← 4KB 경계로 내린 결과 = struct thread 주소
             └─────────────────────┘
```

- 스레드 하나에 페이지 하나를 주고, **맨 앞에 `struct thread`**, **맨 위부터 스택**을 둡니다.
- 그래서 rsp를 페이지 시작으로 내리기만 하면 현재 스레드를 찾습니다.

### `magic`은 왜 있나

> **스택이 넘쳤는지 알려주는 도장입니다.**

- 스택이 위에서 아래로 자라다가 `struct thread`의 맨 끝인 `magic`을 **가장 먼저** 덮어씁니다.
- `THREAD_MAGIC`은 값을 정해 둔 **상수**이고, `t->magic`은 그 값을 복사해 둔 **메모리 4바이트**입니다. 메모리는 보호되어 있지 않아서 다른 데이터가 쓰면 바뀝니다.
- `thread_current()`가 `t->magic == THREAD_MAGIC`인지 검사해서, 다르면 덮어쓰였다고 판단해 멈춥니다.

| 상황 | 결과 |
|---|---|
| 같음 | 안 덮임 (더 아래를 덮었을 가능성은 남음) |
| 다름 | **덮어쓰임이 확실함** |

- 큰 지역 배열이나 깊은 재귀가 원인이 됩니다. 큰 데이터는 `malloc`을 씁니다.

## 13. 락은 어떻게 동작하나

> **`lock_init`은 락을 걸지 않습니다. 사용할 수 있게 준비만 하고, 걸리는 건 `lock_acquire`입니다.**

Pintos의 락은 **값이 1인 세마포어 + 쥔 스레드(holder)** 로 만들어져 있습니다.

| 함수 | 세마포어 값 | holder | 상태 |
|---|---|---|---|
| `lock_init` 직후 | 1 | NULL | 비어 있음 |
| `lock_acquire` 후 | 0 | 쥔 스레드 | 잠김 |
| `lock_release` 후 | 1 | NULL | 비어 있음 |

- 이미 잠겨 있을 때 다른 스레드가 `acquire`하면 **대기 줄(waiters)** 에 들어가 잠듭니다. `release`되면 대기 중이던 스레드가 락을 이어받습니다.
- 락은 **쥔 스레드만** `release`할 수 있습니다. 그래서 `lock_release`에 `lock_held_by_current_thread` 검사가 있습니다.
- 값 0 또는 1만 가지는 락과 달리, 세마포어는 아무 스레드나 올릴 수 있고 2 이상도 됩니다.

## 14. 알람 테스트 6개

> **같은 `test_sleep()`을 인자만 바꿔 쓰는 테스트가 3개, 나머지는 각자 따로 있습니다.**

| 테스트 | 배점 | 무엇을 확인하나 | 잡는 버그 |
|---|---|---|---|
| `alarm-single` | 1 | 스레드 5개가 각자 다른 시간을 **1번** 자고 시간 순서대로 깨어나는가 | 일찍/늦게 깨우거나 순서가 뒤바뀜 |
| `alarm-multiple` | 1 | 같은 스레드가 **7번 반복**해서 자도 순서가 맞는가 | 다시 잘 때 깨울 시각 계산 오류 |
| `alarm-simultaneous` | 1 | 같은 시각에 깨어나야 하는 스레드 3개가 **같은 틱에** 깨어나는가 | 한 번에 하나만 깨우고 끝냄 |
| `alarm-priority` | 2 | 같은 시각에 깨어난 스레드들이 **우선순위 높은 순**으로 실행되는가 | ready_list가 우선순위를 안 봄 |
| `alarm-zero` | 1 | `timer_sleep(0)`이 바로 돌아오는가 | 0틱을 재워서 영영 안 깨어남 |
| `alarm-negative` | 1 | `timer_sleep(-100)`에서 죽지 않는가 | 음수로 시각을 계산해 오동작 |

### `test_sleep`가 순서를 검사하는 방법

- 깨어난 스레드가 자기 번호를 기록 칸에 순서대로 적습니다.
- 마지막에 **(몇 번째 깸) × (자는 시간)** 이 줄어들지 않는지 봅니다. 이 값이 "깨어난 시각 − 시작 시각"과 같아서, 줄어들지 않는다는 것은 시간순으로 깨어났다는 뜻입니다.
- 모든 스레드가 같은 기준 시각(`start`)에서 출발하도록 `start = 지금 + 100`으로 정합니다. 스레드를 만드는 동안 시각이 흘러도 기준이 과거가 되지 않게 하는 여유입니다.

> **`alarm-priority`**는 알람 클럭만으로는 통과하지 못할 수 있습니다.
> 깨어난 스레드를 우선순위 순서로 실행하는 **우선순위 스케줄링**이 필요하기 때문입니다.
> 알람 클럭을 구현한 직후에는 이 테스트만 FAIL이어도 정상입니다.

## 15. 구현 순서 체크리스트

| 순서 | 파일 | 할 일 |
|---|---|---|
| 0 | 터미널 | 고치기 전에 기존 테스트 상태를 기록 |
| 1 | `thread.h` | `struct thread`에 **깨울 시각** 멤버 추가 |
| 2 | `timer.c` 위쪽 | `static struct list sleep_list;` 선언 |
| 3 | `timer_init()` | `list_init`으로 `sleep_list` 초기화 |
| 4 | `timer.c` | 깨울 시각을 비교하는 **비교 함수** 작성 (새 이름, `static`) |
| 5 | `timer_sleep()` | 깨울 시각 저장 → 정렬해서 삽입 → 잠들기 (인터럽트를 끈 채로) |
| 6 | `timer_interrupt()` | 맨 앞부터 깨울 때가 된 스레드를 `thread_unblock` |
| 7 | 테스트 | 알람 6개와 `idle ticks` 확인 |

### 순서가 중요한 부분
- **깨울 시각은 잠들기 전에 저장**합니다. 잠든 뒤에는 그 줄이 실행되지 않습니다.
- `timer_sleep` 시작에서 `ticks <= 0`이면 **바로 반환**합니다. 안 그러면 `alarm-zero`/`alarm-negative`에서 영영 안 깨어납니다.
- 인터럽트를 끄는 구간은 **정렬 삽입과 잠들기를 한 덩어리**로 묶습니다.
- 깨울 때는 `if`가 아니라 **맨 앞이 안 될 때까지 반복**합니다.
- 인터럽트 처리 안에서는 `thread_unblock`은 쓸 수 있지만 `thread_yield`는 쓸 수 없습니다.
- 기존 함수의 **시그니처는 바꾸지 않고**, 새 멤버와 새 함수만 추가합니다.

### 검증
1. 알람 6개가 모두 통과하는지 봅니다. `alarm-priority`만 실패해도 정상입니다.
2. `idle ticks`가 **크게 늘었는지** 봅니다. 구현 전에는 `alarm-single`이 0이었는데, 구현 후에는 200 이상이 나와야 합니다. 0 근처라면 여전히 busy waiting입니다.

| 테스트 | 구현 전 Timer | 구현 전 idle ticks |
|---|---|---|
| alarm-single | 278 | 0 |
| alarm-multiple | 590 | 0 |
| alarm-simultaneous | 283 | 0 |
| alarm-priority | 526 | 0 |
